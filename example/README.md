# Example: STM32F407VG Discovery Board

This folder contains a complete, pre-generated Exhibition project targeting the
**STM32F407VG Discovery** board. It is intended as a working reference you can
build and run immediately, and as a starting point for understanding how
Exhibition-generated projects are structured.

Two projects are generated side-by-side:

| Directory | Role | Runs on |
|---|---|---|
| `rt/` | Remote Terminal firmware | STM32F407VG Discovery board |
| `bc/` | Bus Controller host app | Linux, macOS, or Windows PC |

The RT firmware listens on **USART2** for commands from the BC host app. The BC
app provides a typed C++ API — one method per peripheral operation — that drives
the board over a serial connection.

## Prerequisites

| Item | Purpose |
|---|---|
| STM32F407VG Discovery board | Target hardware |
| STM32CubeIDE 1.14+ | Build and flash the RT firmware |
| CMake 3.15+, Ninja, and a C++17 compiler (GCC/Clang on Linux/macOS; MSVC or MinGW on Windows) | Build the BC host app |
| USB-UART adapter or ST-LINK virtual COM port | Serial link between PC and board |
| C++17 support in your toolchain | Required by both projects |

## Hardware Configuration

The example was generated from `rt/discovery_f4.ioc`. The peripherals configured
in that file and their assigned sub-addresses are:

| Sub-address | Peripheral | HAL handle / pins | Label in .ioc |
|---|---|---|---|
| 1 | System | — | fingerprint, device count |
| 2 | ADC | hadc1 ch1 (PA1) | MyAdc |
| 3 | CAN | hcan1 | — |
| 4 | GPIO Input | Bank B (PB2) | BOOT1 |
| 5 | GPIO Input | Bank D (PD5) | OTG_FS_OverCurrent |
| 6 | GPIO Output | Bank C (PC0) | OTG_FS_PowerSwitchOn |
| 7 | GPIO Output | Bank D (PD4, PD12–PD15) | PD4, LD4/LD3/LD5/LD6 (LEDs) |
| 8 | GPIO Output | Bank E (PE3) | MEMS CS |
| 9 | I2C | hi2c1 | — |
| 10 | RTC | — | — |
| 11 | SPI | hspi1 | MEMS accelerometer |

The per-sub-address YAML manifests under `bc/api/` and `rt/Core/Src/rt/api/`
document every opcode and payload shape in detail.

## Building and Running

### Step 1 — Flash the RT firmware

1. Open STM32CubeIDE and import `example/rt/` as an existing project
   (**File → Import → Existing Projects into Workspace**).
2. Set the C++ language standard to C++17 in the project properties
   (**C/C++ Build → Settings → MCU G++ Compiler → Language standard**).
3. Wire the RT into `Core/Src/main.c` (or `.cpp`). Exhibition does this for you
   when it generates the project — it inserts these three lines, each inside its
   `USER CODE` fence, and skips any already present:
   ```cpp
   #include "rt/device_registry.h"

   // After HAL_Init() and peripheral MX_*_Init() calls:
   init_rt();

   // Inside the main while(1) loop:
   tick_rt();
   ```
   If the generator couldn't find `main.c` or a `USER CODE` region was missing,
   it tells you exactly what to paste in; add those lines by hand.
4. Build and flash the board.

See `rt/Core/Src/rt/INTEGRATION_GUIDE.md` for full step-by-step instructions,
including how to configure USART2 as the control bus and how to enable C++17 in
CubeIDE.

### Step 2 — Build the BC host app

```sh
cd example/exhibition_bc
cmake --preset Debug
cmake --build --preset Debug
```

The binary is written to `build/Debug/exhibition_bc` (or
`build/Debug/exhibition_bc.exe` on Windows). The build uses CMake + Ninja and
the same command on every platform; it requires no external libraries —
`termios` is part of libc on Linux/macOS, and `ReadFile`/`WriteFile` from
`kernel32.dll` are used on Windows.

### Step 3 — Run the BC host app

```sh
# Linux / macOS
./build/Debug/exhibition_bc /dev/ttyUSB0 115200

# Windows (PowerShell or cmd)
.\build\Debug\exhibition_bc.exe COM7 115200
```

**Expected output (abbreviated):**

```
Fingerprint OK (0xA084EED3)
RT reports 11 registered devices.
Time sync: offset = 0.123, path delay = 0.456 (units 1e-6 s)
MEMS: LIS3DSH detected
MyAdc = 1024 counts @ 312 ms
RTC: 2026-06-03 14:22:01
...
```

The program runs 2000 loop iterations and then exits.

## Code Walkthrough

The demo sequence lives in `exhibition_bc/main.cpp`. The regions between
`USER CODE BEGIN`/`END` markers are the parts you are expected to edit; they
are preserved when the project is regenerated by Exhibition.

### Startup and compatibility check

```cpp
client.soft_reset();   // reset RT state machine
// ...
if (client.verify_fingerprint() != Status::Ok) {
    // Localize the mismatch: per-service hashes pinpoint which
    // sub-address(es) diverged (each is logged as ERROR).
    client.verify_service_hashes();
    return 3;
}
client.get_device_count(count);
```

Exhibition checks API compatibility at two levels. The **fingerprint**
(`0xA084EED3`) is a 32-bit FNV-1a hash over all manifest files; both RT and BC
embed the same constant, and `verify_fingerprint()` reads it back from the RT's
system handler — a single comparison that confirms the whole API matches. A
mismatch means the two projects were generated at different times, so the demo
aborts.

When the fingerprint differs, `verify_service_hashes()` localizes the
divergence: it reads each sub-address's **per-service hash** via the universal
`GET_SERVICE_HASH` command (opcode `0x00`) and compares it to the compile-time
`kServiceHash<Kind>` constant in `service_hashes.h`, logging exactly which
handler(s) differ.

### Time synchronization

```cpp
for (int i = 0; i < 50; ++i) {
    client.sync_once(&m);
}
```

An NTP-style four-timestamp clock-sync exchange measures the RT systick offset
relative to the host clock (the RT stamps both when it receives the probe and when
it sends the reply, so its own handling time drops out). Running it 50 times lets
the on-board estimator converge. After this the BC knows how to translate RT
timestamps into host-relative times.

The host and the STM32 are independent oscillators with slightly different rates,
so the raw `offset` (BC − RT) does **not** settle to a constant — it ramps by tens
of ppm forever. That drift is physical, not a bug. On the RT each exchange's
`(offset, path delay)` feeds a sliding 8-deep **min-delay clock filter** (the way
NTP rejects jittery round trips): the lowest-delay sample of the recent window is
the one disciplined into the clock, so a single slow exchange never steers it. The
RT then fits a sliding window of those selected measurements to recover both the
offset **and** the clock skew (slope), and disciplines `now_bc_ms()` with the rate
term so RT timestamps stay aligned to the host clock between syncs instead of
drifting. The loop prints the BC-side view (the printed `path delay` is the
filtered min-delay value):

```
Time sync: offset = -12.000 ms, skew = -49.83 ppm, residual = +0.012 ms, path delay = 0.500 ms
```

Watch the **skew** settle to a roughly constant ppm and the **residual** settle
toward zero; the raw `offset` keeps moving by design.

### MEMS accelerometer (SPI)

The `user/mems.cpp` helper demonstrates multi-step SPI interaction:

1. `mems_identify()` reads the WHO_AM_I register via `client.spi_hspi1` to
   detect whether the chip is an LIS302DL, LIS3DSH, or LIS3DH.
2. `mems_init()` sends the power-on and axis-enable command bytes.
3. `mems_update()` reads 6 bytes of X/Y/Z acceleration data in the main loop.

SPI chip-select (PE3, sub-address 8 GPIO Output Bank E) is asserted and
de-asserted manually around each transfer.

### ADC sampling

```cpp
client.adc_hadc1_ch1.sample(adc_counts, adc_timestamp_ms);
```

Returns a 12-bit count and a RT-side millisecond timestamp in a single blocking
call.

### RTC

```cpp
rtc_now_local(rtc_now);      // read host PC wall clock
rtc_set(client, rtc_now);    // program the on-target RTC
rtc_read(client, nullptr);   // read it back and print
```

The helper in `user/rtc.cpp` converts `std::tm` fields to the RTC register
encoding (years since 2000, weekday 1 = Monday).

### LED loop

```cpp
leds_do_loop(client, 10);   // flash PD12→PD13→PD14→PD15 with 10 ms delay
```

The helper in `user/leds.cpp` drives sub-address 7 (GPIO Output Bank D) by
calling `set()` and `clear()` on each pin in sequence.

## User Helper Modules

Three reusable helper modules live in `bc/user/` (and mirrored in `docs/` as
reference copies):

| File | What it does |
|---|---|
| `user/leds.h` / `leds.cpp` | Flash the four Discovery LEDs (PD12–PD15) in sequence |
| `user/mems.h` / `mems.cpp` | Identify, initialize, and read the LIS3x MEMS accelerometer over SPI |
| `user/rtc.h` / `rtc.cpp` | Sync the on-target RTC from the host PC's local time and read it back |

These files are **not** regenerated by Exhibition — they are yours to modify. Use
them as templates when you write custom test sequences for your own boards.

## Regenerating the Example

If you change `discovery_f4.ioc` or update Exhibition itself you can regenerate
both projects in place. Exhibition is interactive — run it from the repository root
and respond to its prompts:

```sh
cargo run --release
```

When prompted:
1. **STM32CubeMX project root** — enter `example/rt` (Exhibition will auto-detect
   `discovery_f4.ioc` inside it).
2. **Transport selection** — choose `USART2` (the transport used by this example).
3. **Generate BC project?** — answer `Y`.
4. **BC output root** — enter `example` (the BC project is written to `example/bc/`).

Generated files are overwritten. Content inside `USER CODE BEGIN`/`END` blocks
in `main.cpp` is preserved. The `user/` helper modules are never touched.
